# Build system

## Executive Summary

- `lwpt build` is the single root entry point. Bare invocation builds
  every `[build]` target in `lwpt.toml`; positional names select targets.
- Development is the default; `--mode release` selects release settings.
- Every binary lands under `build/`, which is gitignored.
- `source/units/Version.inc` is generated by a `prebuild` hook from the
  manifest — the manifest is the single source of truth for the version.

## Entry point

```bash
lwpt build                        # dev build, every target
lwpt build wasmlight              # one target
lwpt build wasmlight wasmbench    # several
lwpt build --mode release         # release settings
lwpt build --clean                # force a full rebuild
lwpt build --jobs 4               # cap concurrent targets
```

Do not invoke `fpc` directly; the one supported form is
`fpc @lwpt.cfg <program>.pas`, and `lwpt.cfg` is itself generated by
`lwpt install`.

## Targets

| Target | Source | Output |
| --- | --- | --- |
| `wasmlight` | `source/apps/wasmlight.pas` | `build/wasmlight` |
| `wasmlight-shell` | `source/apps/wasmlight-shell.pas` | `build/wasmlight-shell` |
| `wasmbench` | `source/apps/wasmbench.pas` | `build/wasmbench` |
| `wasmspec` | `source/apps/wasmspec.pas` | `build/wasmspec` |

Test programs are not `[build]` targets — `lwpt test` discovers, compiles,
and runs `source/units/*.Test.pas` independently. Release archives are
packed by `scripts/pack-release.pas` after `lwpt build`; they are not a
`[build]` entry. See [deployment.md](deployment.md).

## Compiler settings

All project-wide directives live in `source/units/Shared.inc`, included by
every unit and program. Delphi mode, `{$H+}`, and the dev/release split:
release (`-dPRODUCTION`) turns on inlining and turns off overflow, range,
stack, and object checks; development turns them all on. Never repeat
these directives per unit, and never add a second include with a
different baseline.

`Shared.inc` also sets `{$optimization noorderfields}` in every mode.
Release builds compile with `-O4`, which otherwise reorders class fields
to pack them. The JIT and AOT tiers bake class field offsets into machine
code, and `Wasm.Target` publishes them for `.waot` artifacts and native
executables. Reordering moved those offsets in release builds only, so a
release runtime accepted a dev-built artifact and then faulted. As a second
line of defence, a build whose live layout differs from the published one
refuses to stamp artifacts for any target and rejects every
published-layout artifact. `[test].flags = ["-O4"]` compiles the unit tests
at release's optimization level, so `Wasm.Target.Test` checks the release
layout directly; development checks stay on.

## A WebAssembly host (lakon)

wasmlight also compiles to a wasm32 WASI command with
[lakon](https://github.com/frostney/lakon), an Object Pascal compiler that
targets WebAssembly, so a wasmlight host can run inside another WebAssembly
runtime. lwpt does not drive lakon yet, so this build is a cross-check run by
hand, not a `[build]` target:

```bash
lakon compile source/apps/wasmlight.pas -Fu source/units \
  -Fu .lwpt/modules/cli/packages/cli/source -o build/wasmlight.wasm
node <lakon>/tests/support/run-wasi.mjs --dir tests/fixtures/wasi::/f \
  build/wasmlight.wasm run /f/hello.wasm
```

`wasmlight-shell` and `wasmspec` build the same way. `wasmbench` does not
compile: it builds its synthetic modules in a `TMemoryStream`, which lakon's
`Classes` lacks, and it measures native call gates and the JIT, which a
WebAssembly host does not have anyway.

lakon defines `LAKON`, `WASI`, `CPUWASM`, and `CPUWASM32`, and `Shared.inc`
derives the host's capabilities from them:

- `WASM_TRAPS_RAISE` (any wasm CPU target): traps raise instead of jumping
  to the trampoline
  ([ADR-0020](adr/0020-a-webassembly-host-raises-traps-directly.md)). The
  host is interpreter-only: the JIT, AOT, and native call gates need a
  64-bit UNIX host.
- `WASM_HOST_WASI` (a WASI target): the outer runtime is the only operating
  system. With no `realpath`, `lstat`, or CSPRNG to reach, `Wasm.Wasi` fails
  closed: a `--dir` preopen is still advertised, and `fd_readdir` and
  `fd_filestat_get` on the preopen itself still work, but every path under
  it answers `ENOENT`, and `random_get` answers `EIO`.
- No second thread bumps the epoch, so a runaway guest is not interrupted.
- An exhausted heap traps the whole host: lakon's allocator cannot raise
  `EOutOfMemory`, so the collector's recovery path never runs.

A wasmlight string holds UTF-8 bytes, one per character. Under lakon a
character is a UTF-16 unit, so each byte rides in its own unit; `Move`
between byte and character elements copies byte for byte under both
compilers. Names and paths outside ASCII therefore differ from the native
host where lakon hands a string to the outer runtime.

## Generated version constant

```toml
[prebuild]
stamp-version = { command = "instantfpc",
                  args = ["scripts/stamp-version.pas"],
                  inputs = ["lwpt.toml"],
                  output = "source/units/Version.inc" }
```

LWPT 0.6 runs lifecycle hooks as explicit commands, so the manifest selects
`instantfpc` and passes `scripts/stamp-version.pas` as its first argument. The
script writes
`PROGRAM_VERSION` from `[package].version` in `lwpt.toml`, or from
`$WASMLIGHT_VERSION_OVERRIDE` when set — which is how a release build
stamps the git tag into the binary. `Wasm.Core` includes the result.

The same hook is registered under `[pretest]`, because the test programs
compile `Wasm.Core` too.

`Version.inc` is committed even though it is generated, so a fresh clone
compiles before any hook has run. Never hand-edit it: change the manifest
version and let the hook restamp.
